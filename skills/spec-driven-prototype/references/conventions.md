# 原型十铁律

> **解决什么问题**：这类项目翻车的地方高度集中，就这十条。每条给出「一句话规则 + 真踩过的反例 + 怎么落地」，开工前贴出来，评审时逐条对照。

| # | 铁律 | 一句话理由 |
| --- | --- | --- |
| 1 | 规格是唯一事实源，原型字段不许手写 | 两套字段模型必然漂移 |
| 2 | 改源不改产物 | 直接改产物，下次重跑就没了 |
| 3 | 一个菜单项 = 一类单据（含明细与报表视图） | 三拆或按部门拆，都是把报表页当菜单 |
| 4 | 字段与来源系统逐字一致 | 含错别字；改了就对不上接口 |
| 5 | 字段标来源三类 | 用户要一眼看出哪些不用填 |
| 6 | 起单锚点按业务定，不照抄老系统 | 这是业务决策，不是界面问题 |
| 7 | 兜底入口必须留痕 | 原因必填 + 可事后补关联 + 列表可筛 |
| 8 | 原型不写业务规则 | 口径一改，原型变成错误信息源 |
| 9 | 列表铺满 + 分页 + 列配置；详情是独立页面 | 弹窗装不下几十个字段，也不能被链接 |
| 10 | 自检断言旧口径词为 0 | 旧词会散落在文档和原型里，让脚本报错 |

---

## 1. 规格是唯一事实源，原型字段不许手写

**规则**：原型里的字段、枚举、必填、明细行列集，只能来自规格生成物；页面文件里不许再出现手写的字段数组。

**反例**：早期原型由前端手写，一页列的字段只有十几个；而规格里同一页有上百个字段。两边看起来都「像那么回事」，直到做字段级对账才发现大面积缺失——修的时候要重写页面。

**落地**：

- 生成物文件头写明「自动生成，勿手改 + 源路径 + 重新生成命令 + 日期」。
- 页面只从生成物取值（页面字段集 / 明细行列集），组件接收字段数组，页面不内联字段名清单。
- 对账脚本按页比对「规格字段 → 页面源码里的写法」，真缺的必须清零。

## 2. 改源不改产物

**规则**：要改口径、改字段、改页面，一律改源 JSON 后重跑生成链；产物（规格 JSON、Excel、字段集、列集、路由、权限）都是可重生成的。

**反例**：图省事直接编辑生成的 Excel 或字段集文件，当时页面确实变了；换人重跑一次生成链，改动全部消失，而且没人知道丢的是什么。

**落地**：

- 每个产物文件头写重生成命令；文档里写清「源是哪个文件」。
- 生成脚本做成**幂等**：连跑两遍，源与规格 JSON 哈希一致。
- 一次性修正脚本也保留（带断言、可重复执行），下次审计能看到当时到底改了什么。

## 3. 一个菜单项 = 一类单据（含它的明细表与报表视图）

**规则**：菜单按单据类型分。一类单据 = 一个菜单项，它的明细表、报表视图、操作页都挂在它下面，不再单独占菜单。

**反例**：把一类单据拆成「台账 / 处理 / 明细」三个菜单项——用户点三次才走完一件事；或者把只有队列、没有自己详情的**跨单据作业台**当成一类单据——点进去发现是别人的详情页，名实不符。

**落地**：

- 每个菜单项必须能指到一个单据实体 + 一个详情页。指不到的，就不该是菜单项。
- 跨单据作业台保留在菜单里时，页头明确标注「队列作业台 · 详情看原单」，行点击进原单详情。
- 操作页（新建/审单/变更/发货指令）挂在锚点对象的上下文路由下（形如 /对象/:id/动作），不占菜单。

## 4. 字段与来源系统逐字一致

**规则**：字段名、枚举取值、必填标记，全部照抄来源系统；含错别字、含并格拆开后的原文、去掉尾部冒号。**不做顺手修正。**

**反例**：把来源系统的「竟标价」改成「竞标价」、「己出货数量」改成「已出货数量」。界面看着更规范，但接口映射按原文匹配，这两个字段直接取不到值。实测来源系统里有 4 处这类错别字。

**落地**：

- 字段名入库用原文；需要正确写法时另开「建议写法」列旁边标注。
- 抽取脚本不跑拼写检查、不做同义词归一。
- 同一概念在来源系统有两种写法时两条都保留，不合并。

## 5. 字段标来源三类

**规则**：每个字段标记它从哪来——**外部引用**（从外部系统带出，只读）/ **本单录入** / **系统计算**（永远只读）。

**反例**：外部引用的客户、项目、合同字段在表单上是可编辑输入框。用户改了之后，本单数据和来源系统不一致，后续回写/对账冲突，而且没人知道哪个是准的。

**落地**：

- 生成器内置三类字段名单（可读、可评审），生成时打 src 标记。
- 组件按 src 渲染：外部引用默认只读（需要时给一个「复核后可改」开关，并记录改动），系统计算永远只读。
- 表单上给来源角标（例：引用 / 录入 / 系统），配一句图例说明。

## 6. 起单锚点按业务定，不照抄老系统

**规则**：新系统从哪个对象起单（项目 / 客户 / 合同），是业务决策。老系统以客户为中心，新系统可能以项目为中心——**不要照抄**。

**反例**：照抄老系统从客户起单，而新业务要求按项目归集与销售归属。结果订单一多就分不清属于哪个项目，报表做不出来，只能回头改规格和页面。

**落地**：

- 开工前问清：起单锚点是什么？锚点对象有哪些字段要带出？
- 锚点字段设为必选、且不可手填；其余对象（客户/合同/收货信息）由锚点带出，可复核修改。
- 锚点归属的字段在下单时**存快照**（例：实际销售经理 / 实际销售部门），与「现有」归属分列——人员调动后历史单据不变。

## 7. 兜底入口必须留痕

**规则**：允许不经外部系统直接建单，但必须做到三件事：**原因必填**、**可事后补关联**、**列表可筛**。

**反例**：给了「直接建单」这个逃生口，但没要求填原因、也没留补关联的位置。月底对账时发现几张来源不明的单据，没人知道该挂到哪个项目上，也没法查是谁建的。

**落地**：

- 起单方式三选一：锚点起单 / 客户起单 / 直接建单；选直接建单时必须选原因（下拉：外部系统未建档 / 客户要求先下单 / 历史补录 / 应急 / 其他）。
- 留一个「补关联对象」输入；未补的自动标记「待补关联 = 是」，补上后改否。
- 列表加「起单方式」「待补关联」两列 + 一个快捷筛选项，让异常单据一眼可见。

## 8. 原型不写业务规则

**规则**：规则、口径、状态定义只写需求文档。原型里只允许五类文字：**操作提示、校验反馈、空态、实时计算结果、短指标标签**。

**反例**：把「签单即放行、不另设独立审批」「单据状态只有三个」「已核准等于已出库」这类口径写进原型文案。口径一改，原型立刻变成错误信息的来源，而且散落在几十个页面里，改不干净。

**落地**：

- 页面文案只描述「当前这个动作会发生什么」，不描述「业务为什么这样」。
- 口径写进规格需求表的规则列；需要让人在界面上看到时，用短标签 + 悬浮说明指回需求编号。
- 审计脚本搜口径关键词（状态机词、审批词），命中就报出来人工判断。

## 9. 列表铺满 + 分页 + 列配置；详情是独立页面

**规则**：列表页占满可视高度、带分页、列可配置；详情页是**独立路由页面**，不是弹窗。

**反例**：详情做成弹窗——几十个字段塞不下、不能收藏、不能分享链接、刷新后回到列表；列表不铺满，底部大片空白还要在里面滚动；没有分页，上千行直接卡死。

**落地**：

- 列表容器用弹性高度撑满可视区，表格内部滚动，分页大小 20/50/100/200。
- 详情用独立路由 /对象/:id，支持直接打开与刷新；区块多于 3 个时用页签，不纵向堆成长页。
- 列配置抽屉对列表列与明细行列分别生效（见 [line-config.md](line-config.md)）。

## 10. 自检断言旧口径词为 0

**规则**：把旧口径词写成词表，自检脚本扫描规格全量 JSON 与原型源码，命中就 exit 1。

**反例**：口径从「旧叫法」改成「新叫法」之后，旧词仍散落在文档、字段名、字典与原型里；两种叫法并存，接口对字段时按哪个都可能出错。实测一次口径统一里，旧叫法有 40 处需要清理。

**落地**：

- 词表 = 旧口径词数组；白名单 = 否定句（例：保留「不另设独立放行审批」这句，因为它是新口径的否定表述）。
- 自检脚本对规格 JSON 做全量字符串扫描；原型侧对页面源码扫描。
- 口径变更的提交里必须同时更新词表，否则下次断言抓不到这次的旧词。

## 铁律 → 由什么断言

| 铁律 | 断言方式 |
| --- | --- |
| 1 规格唯一事实源 | 字段级对账脚本（规格字段 → 页面源码），真缺清零 |
| 2 改源不改产物 | 幂等检查：连跑两遍哈希一致；产物文件头含「勿手改」 |
| 3 一个菜单项 = 一类单据 | 菜单项 → 页面ID → 详情页 三层可解析；「—」菜单归属的页面有进入路径 |
| 4 逐字一致 | 抽取脚本无拼写检查；字典取值与来源文本逐字比对 |
| 5 来源三类 | 生成物里每个字段都有 src 标记，且取值在三类之内 |
| 6 锚点固定 | 锚点字段 required = 是且不可编辑；归属字段有快照列 |
| 7 兜底留痕 | 直接建单分支断言「原因必填」；列表含「待补关联」筛选 |
| 8 不写业务规则 | 页面源码口径关键词扫描 |
| 9 列表与详情形态 | 审计脚本：列表含分页组件、详情页为独立文件、含弹窗的页面登记用途 |
| 10 旧口径词为 0 | 词表全量扫描（JSON + 页面源码），否定句白名单 |
