# PRD工作流

## 何时使用

产品Brief或项目诊断已通过，需要形成可评审、可开发、可测试的需求基线。

## 先选文档等级

| 等级 | 适用 | 必要内容 |
|---|---|---|
| L1 一页纸Brief | 单功能、低风险、先验证 | 用户、痛点、范围、验证、不做 |
| L2 轻量PRD | 单模块迭代、单团队交付 | 目标、流程、页面、字段、规则、权限、验收、不做 |
| L3 完整PRD | 新产品、跨团队、重大版本、高风险 | 完整章节、里程碑、商业逻辑、风险、追溯关系 |

默认使用L2。只有跨团队、重大预算、合规或全新产品才使用L3，禁止小需求机械套12章。

## 使用规范

- 先读“何时使用”和“输入门禁”，再执行步骤。
- 缺失关键输入时，只列信息缺口，不自行补造。
- 输出必须包含结论、边界、明确不做和可验证标准。


## 执行步骤

1. 明确目标、用户和成功指标。
2. 画主流程、异常路径和状态变化。
3. 拆页面、动作、字段、权限与业务规则。
4. 写性能、安全、可用性等量化非功能需求。
5. 写验收标准、依赖、风险和不做清单。
6. 建立业务目标→需求ID→验收用例追溯。

## 原完整PRD方法

### 1.1 PRD 标准写法

**什么时候用**：新产品立项、大版本迭代、跨团队协作的功能开发。

#### 12 章结构详解

每一章写什么、怎么写、写多长：

##### 第一章：产品定位

写一段话说清产品是什么，再加一张表：

```
【一句话定义】
[产品名]是一款面向[目标用户]的[产品类型]，帮助用户解决[核心问题]。

【价值主张表】
| 用户类型 | 核心价值 | 解决了什么痛点 |
|----------|---------|---------------|
| 【角色A】 | 【具体价值】 | 【具体痛点】 |
| 【角色B】 | 【具体价值】 | 【具体痛点】 |

【产品形态】
形态：[APP/Web/小程序/硬件/...]
```

**示例**（已脱敏）：
```
CRM助手是一款面向销售团队的项目管理工具，帮助销售避免撞单、规范报备流程。

| 用户类型 | 核心价值 | 解决了什么痛点 |
| 一线销售 | 自动检测项目冲突 | 不知道项目是否已被其他人报备，白忙一场 |
| 销售总监 | 项目全链路可视 | 跨区项目谁在跟、跟到哪了，两眼一抹黑 |
```

**常见错误**：只写功能不写用户。——不是"CRM有报备功能"，是"帮销售不用再打电话问同事这个项目有没有人跟"。

##### 第二章：背景信息

回答三个问题：

1. **行业背景**（2-3句话）— 当前行业发生了什么变化？
2. **用户痛点**（细化到角色）— 每个角色具体什么感受？
3. **公司战略定位**（1句话）— 这个产品在公司战略中的位置？

**格式**：
```
### 行业背景
[2-3句话]

### 用户痛点
| 角色 | 痛点 | 频率 | 影响 |
|------|------|:----:|:----:|
| 角色A | 具体描述 | 每天N次 | 损失XX |

### 公司战略定位
[1句话]
```

##### 第三章：产品愿景

```
### 长期愿景（3-5年）
[一句话，产品最终要成为什么]

### 阶段目标（V1.0）
| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|:------:|:------:|:---------|
| 指标1 | XX | XX | 怎么统计 |
```

##### 第四章：业务流程

画核心主流程，标注关键决策节点。

**格式**（用 ASCII 流程图）：
```
[触发条件] → [步骤1] → [步骤2] → [决策节点]
                                 ├── 是 → [步骤3A] → ...
                                 └── 否 → [步骤3B] → ...
```

**加上异常处理**：
```
[异常场景1]：用户网络断开 → 保存草稿 → 重连后自动提交
[异常场景2]：数据冲突 → 提示用户刷新
```

##### 第五章：交互流程

每页写清楚：页面目的 + 页面元素 + 交互逻辑：

```
### 页面名：[页面名称]
**页面目的**：用户在这个页面完成什么任务
**访问路径**：从哪里进入这个页面

| 元素 | 类型 | 说明 | 交互 |
|------|------|------|------|
| 元素名称 | 按钮/输入框/列表 | 展示什么内容 | 点击/输入后发生什么 |
```

##### 第六章：详细需求分解

用需求ID编号，每条写清楚：

```
F-01-01 需求名称
  - 详细描述：[具体描述]
  - 输入：[前置条件/所需数据]
  - 输出：[期望结果]
  - 依赖：[依赖的F编号]
  - 优先级：P0/P1/P2
  - 验收标准：[怎么算做完]
```

##### 第七章：非功能需求

```
| 需求项 | 指标 | 说明 |
|--------|:----:|:-----|
| 页面加载时间 | < 2秒 | 首屏加载 |
| 并发用户数 | ≥ 100 | 同时在线 |
| 可用性 | 99.9% | 全年宕机<8.7小时 |
| 数据安全 | 传输加密 | HTTPS + 字段级脱敏 |
```

##### 第八章：版本规划与里程碑

```
| 版本 | 核心功能 | 里程碑 | 预期时间 |
|:----:|:---------|:-------|:---------|
| V1.0 | P0功能 | 技术验证完成 | 202X年Q1 |
| V1.1 | P1功能 | 用户验收 | 202X年Q2 |
| V2.0 | 全量 | 正式上线 | 202X年Q3 |
```

##### 第九章：红线清单

**每项附理由**，不写"暂时不做"这种模糊理由：

```
| 功能 | 不做理由 | 替代方案 |
|------|---------|---------|
| [功能] | [为什么不做——成本/复杂度/优先级] | [用户可以用什么替代] |
```

**示例**：
```
| 功能 | 不做理由 | 替代方案 |
| 多语言国际化 | 一期用户仅国内，翻译工作量大且维护成本高 | 二期再说，保持代码结构可扩展 |
| 自定义报表 | 一期无足够数据积累，做出来是空架子 | V2.0有三个月数据积累后再做 |
```

##### 第十章：一页纸赚钱逻辑

```
| 收入类别 | 年份 | 用户数/订单数 | 单价 | 总收入 |
|:---------|:----:|:-------------:|:----:|:------:|
| 软件订阅 | 1 | XX | ¥XX | ¥XX |
| 硬件销售 | 1 | XX | ¥XX | ¥XX |
| 运维服务 | 1 | XX | ¥XX | ¥XX |

**续费率底线**：[XX]%
**回本周期**：[XX]个月
```

##### 第十一章：风险登记册

```
| 编号 | 风险描述 | 等级 | 概率 | 影响 | 应对策略 | 责任人 | 状态 |
|:----:|:---------|:---:|:----:|:----:|:---------|:------|:----:|
| R-01 | [风险] | 高/中/低 | 高/中/低 | 高/中/低 | [怎么应对] | [谁] | open/closed |
```

##### 第十二章：附录

```
### 术语表
| 术语 | 定义 |
|:----|:-----|

### 参考文档
| 文档名 | 版本 | 存放位置 |
|--------|:----:|:---------|

### 需求ID索引
| 需求ID | 所属模块 | 优先级 |
|:------:|:--------:|:-----:|
```

#### PRD 写作避坑清单

写完后逐条自查：

- [ ] 每类用户单独写了价值主张，不是一句"提升效率"带过
- [ ] 用户痛点量化了（频率+影响）
- [ ] 业务流程里标了决策节点和异常路径
- [ ] 需求有编号
- [ ] 有红线清单，每项附理由和替代方案
- [ ] 有风险登记册
- [ ] 非功能需求量化了（不是"性能好"这种模糊词）
- [ ] 附录有术语表（避免团队沟通歧义）
