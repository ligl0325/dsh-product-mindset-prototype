# AI 辅助规则拆解与原型评审

用于把已有业务政策或跨模块流程转成可评审、可开发的系统规则。单模块规则可以直接拆；完整项目沿用五级需求结构，以下内容落在「操作 → 规则」层。

## 1. 从业务材料提取规则

- 先定位现行政策、已确认的业务口径、需求和原型版本。让 AI 提取并对照条款，记录来源和分歧。原型只能证明当前演示行为，来源不全或口径冲突时，把相应规则列为待确认。
- 先写系统要做什么判断，再写判断后的动作和权限。每条判定写清规则编号、来源、触发时机、比对字段及取值来源、命中条件、判定结果、后续动作。涉及条件重叠、信息缺失或例外时，明确优先级与处理方式。由业务确认规则口径，产品将已确认规则交给开发和测试。
- 跨模块流程另写交接条件、下游生成或更新的记录、状态归属和结束条件。源事件、派生任务、工单和应急响应分别核对，避免用一个对象的完成状态替代另一对象的结束判断。

**CRM 示例。** 把项目报备政策拆成冲突判定规则，回答「系统比较什么」「什么情况下判为本地或异地冲突」「命中后进哪条处理流程」。处理人及其操作权限写在判定结果之后。具体比对字段、优先级和例外须回到现行政策核实。

## 2. 用交互原型验证规则

- 将确认后的规则、样例数据和评审路径交给 AI 生成原型。优先覆盖会改变业务结果的正常、冲突和例外分支。每条路径写明输入、操作和预期结果，并关联规则编号。例外未定时标明待确认。
- 按用户指定的设备形态和原型格式交付。需要 HTML 转 Axure 时，可按实际可用的转换流程操作，并复核关键页面及交互；仅完成 HTML 时按 HTML 交付记录。
- 评审走查后，把新增或修订的规则同步回需求和验收用例，记录尚未验证的交互、模拟数据及接口范围。

**平安校园示例。** 以一条事件为起点，分别走查创建工单、启动应急预案并生成任务和工单、工单关闭后核对应急结束条件。消息模板与发送渠道可用独立原型走查，真实接口接入和送达另行验证。
