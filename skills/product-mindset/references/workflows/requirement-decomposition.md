# 五级需求拆解工作流

## 何时使用

项目诊断通过，需要把P0范围拆到开发可估时、测试可写用例的粒度。

## 输入门禁

必须已有：业务目标、涉及端、核心角色、主流程、P0边界。缺任一项，先回到项目诊断或PRD。

## 使用规范

- 先读“何时使用”和“输入门禁”，再执行步骤。
- 缺失关键输入时，只列信息缺口，不自行补造。
- 输出必须包含结论、边界、明确不做和可验证标准。


涉及政策判定、跨模块状态或 AI 原型验证时，结合[AI 辅助规则评审](ai-rule-review.md)，把判定和后续动作落到五级规则。

## 强制追溯字段

每条五级规则都必须关联：需求ID、来源、业务目标、角色、操作、字段/状态、权限、验收用例、埋点（如需要）。

## 方法正文

### 2.2 五级需求分解

**什么时候用**：立项评审通过后，把P0功能按「端 → 模块 → 功能组 → 操作 → 规则/约束」逐层拆到可开发、可测试的粒度。

#### 五级结构

| 级别 | 名称 | 拆什么 | 谁写 | 产出物 |
|:----:|:-----|:------|:----|:------|
| **一级** | 端 | 产品落在哪个端（Web/App/小程序/API） | 产品负责人 | 端名称 + 一句话定位 |
| **二级** | 模块 | 端内有哪些业务模块 | 产品经理 | 模块名 + 模块职责（1句话） |
| **三级** | 功能组 | 模块内有哪些功能组（一组相关操作的集合） | 产品经理 | 功能组名 + 功能组描述 |
| **四级** | 操作 | 功能组里有哪些用户操作 | 产品经理 | 操作名 + 触发条件 + 预期结果 |
| **五级** | 规则/约束 | 每个操作的具体业务规则和约束条件 | 产品经理+开发 | 规则列表（字段校验/状态流转/边界条件） |

**层级关系**：
```
一级（端）
 └── 二级（模块）
      └── 三级（功能组）
           └── 四级（操作）
                └── 五级（规则/约束）
```

#### 完整示例（CRM，已脱敏）

**示例一：客户搜索**

```
一级（端）：Web端
  └── 二级（模块）：客户管理
       └── 三级（功能组）：客户搜索

四级（操作）：
  操作1：关键词搜索
    - 触发：用户在顶部搜索框输入关键词，回车或点击搜索图标
    - 结果：跳转搜索结果页，展示匹配客户列表

  操作2：高级筛选
    - 触发：用户点击搜索结果页的「高级筛选」按钮
    - 结果：展开筛选面板，支持按行业/地区/客户等级/跟进状态组合筛选

五级（规则/约束）：
  操作1 - 关键词搜索：
    R-01：支持模糊匹配，输入"张三"可匹配"张三丰""张三思"
    R-02：搜索范围覆盖客户名称、联系人姓名、手机号三个字段
    R-03：输入后 < 2秒返回结果
    R-04：结果按匹配度排序，同等匹配度按最后跟进时间倒序
    R-05：空搜索（仅回车不输入）展示最近查看的10个客户
    R-06：输入特殊字符（如 <>'"&）不报错，返回0结果并提示"未找到匹配客户"

  操作2 - 高级筛选：
    R-07：筛选条件最多同时选5个维度
    R-08：点击「重置」清空所有筛选条件
    R-09：筛选结果实时更新，不需要再次点击搜索
```

**示例二：跟进记录**

```
一级（端）：Web端
  └── 二级（模块）：销售管理
       └── 三级（功能组）：跟进记录

四级（操作）：
  操作1：新增跟进记录
    - 触发：用户在客户详情页点击「新增跟进」按钮
    - 结果：弹出跟进记录表单

  操作2：编辑跟进记录
    - 触发：用户点击已有跟进记录的「编辑」按钮
    - 结果：表单回填原数据，修改后提交

五级（规则/约束）：
  操作1 - 新增跟进记录：
    R-01：跟进方式必填，下拉选项（电话/拜访/微信/邮件/其他）
    R-02：跟进时间必填，默认当前时间，不可选未来时间
    R-03：跟进内容必填，10~500字
    R-04：下次跟进日期选填，选了必须晚于本次跟进时间
    R-05：提交后记录出现在跟进时间线顶部（按时间倒序）
    R-06：关联人字段自动带入当前登录用户，不可修改
```

#### 执行步骤

```
Step 1：确定一级 — 列出本期涉及的端（Web/App/小程序）
  → 产出：端清单 + 各端定位

Step 2：拆二级 — 每个端下划分业务模块
  → 评审：产品团队确认模块边界，避免职责交叉

Step 3：拆三级 — 每个模块内划分功能组
  → 评审：确认功能组划分合理，不遗漏不重叠

Step 4：拆四级 — 每个功能组列出所有用户操作
  → 评审：开发和测试确认操作可理解、可估工期

Step 5：拆五级 — 每个操作写出完整规则/约束
  → 评审：开发确认规则可实现，测试确认规则可验证
```

**铁律**：不要跳级。三级没定好就写五级，一定会有规则找不到归属。

#### 常见错误

- ❌ 四级只写了"正常操作"，漏了异常操作 → 网络断开、数据冲突、并发编辑时怎么操作也要写
- ❌ 五级写"搜索要快""界面要好看" → 必须量化到可测试：< 2秒、首屏加载 < 3秒
- ❌ 五级规则没有编号 → 每条规则加 R-XX 编号，测试直接对应写用例
- ❌ 一级只写了 Web 端忘了其他端 → 多端产品必须逐端检查，App 和小程序可能有独立功能
- ❌ 四级操作不属于三级功能组 → 每个操作必须有明确的归属，"导出客户列表"是"客户列表"功能组下的操作，不是"搜索"下的
