# 原型与业务功能说明校验

## 什么时候用

- 「帮我检查这个原型」「这个页面有什么问题」「原型评审一下」；
- 拿效果图（PNG/JPG）、HTML 原型文件/目录、Axure 导出的 HTML 目录，要一份可落地的优化清单；
- 有业务功能说明（需求文档片段、功能描述），要检查它是否完备、有没有歧义；
- 要核对**原型与业务说明是否一致**。

不用于：生成原型或页面（用 `quick-prototype`）、拆需求出需求表（用 `requirement-analysis`）、写 PRD（用 `product-mindset`）。

## 输入与前置

先确认三件事，缺哪件就问一句，不要猜：

1. **被评审对象**：图片 / HTML 文件或目录 / Axure 导出目录 / 只有文字描述。
2. **业务功能说明**：有就一起校验一致性，没有就只评原型。
3. **设计规范**（可选）：终端、Web、App 规范文档；有规范按规范判，没有按通用原则判。

读取方式：

- HTML 原型：用文件读取工具直接读源码（结构、文案、交互脚本都能看到），**不需要额外依赖**；页面多时先列页面清单再逐页评。
- 图片：直接看图，逐字提取可辨认文字；模糊处标「无法辨认」，不要脑补文案。
- Axure 目录：先按文件名列出页面清单，确认评审范围，再逐页取内容或截图。

## 六维度校验

每个维度都要**落到具体位置**（页面名 + 区块/元素 + 原文字），禁止只说「整体感觉不好」。

### 1. 页面完整性

- 核心功能页面是否齐（列表、详情、新增/编辑、结果页）；
- 全局说明、图例、术语表是否齐；
- 异常与边界页面是否覆盖：空数据、无权限、加载中、失败重试、超时；
- 是否存在只有入口没有落地页的「断头路」。

### 2. 布局排版

- 信息层次：一屏内是否能看出主次（标题 > 关键指标 > 明细）；
- 间距与对齐：卡片内边距、表单项标签对齐、栅格是否统一；
- 一致性：同类页面的头图、筛选区、表格列宽是否一致；
- 可读性：正文 ≥ 12px（大屏 ≥ 20px）、对比度不足、长文本截断是否有提示；
- 有设计规范时，逐条对照规范判符合性，不符的写清「规范条款 vs 现状」。

### 3. 功能逻辑说明完整性、正确性

- 页面上的引导文案、按钮文案、字段说明是否说清「做什么、点了会怎样」；
- 术语是否统一（同一对象在不同页面是否换了叫法）；
- 是否有占位内容残留（测试、xxx、lorem、假数字被写成事实）；
- 说明与页面实际行为是否一致（写了可筛选但页面没有筛选器）。

### 4. 交互与业务逻辑

- 主流程是否闭环：每一步都有下一步的明确出口；
- 状态反馈：提交后是否有成功/失败提示、按钮是否防重复点击；
- 异常处理：失败、超时、并发、越权是否有可理解的提示与恢复路径；
- 空状态：是否有引导文案而不是一片空白；
- 危险操作（删除、批量）是否有二次确认；
- 安全类产品（应急广播、医疗设备）额外检查优先级抢占、确认机制。

### 5. 设计创新性（给建议，不作否决项）

- 指出 1~3 处可强化业务特征的地方（信息组织、图表选择、关键操作前置）；
- 只给低成本高收益的建议，不给「重做一套设计系统」这类空话。

### 6. 内容正确性

- 错别字、标点混用（中英文标点）、数字格式（单位、千分位、小数位）；
- 时间/金额/百分比口径是否写清；
- 术语与业务说明是否一致。

## 业务功能说明校验

| 检查项 | 要点 |
| --- | --- |
| 核心要素 | 功能目标、适用场景、操作主体、输入输出、边界条件是否都写了 |
| 逻辑完整性 | 流程是否闭环，有无断裂或自相矛盾 |
| 细节补充 | 特殊规则、异常处理、与其他功能的关联是否说明 |
| 表述歧义 | 模糊词（尽快、较多、适当）、指代不明（它、该功能）、范围不明（部分用户） |

## 跨模块一致性

- 原型的页面/模块清单 vs 业务说明的功能清单，是否有一方多一方少；
- 同一流程两边的步骤顺序是否一致；
- 元素命名、术语是否一致（原型叫「工单」说明里叫「任务」就是问题）。

## 报告结构（固定）

```markdown
# <原型名称> 原型校验报告

## 一、原型概览与整体评估
- 评审对象：<文件/目录/图片清单>
- 评审范围：<页面数、是否含业务说明、是否有规范>
- 评估等级：A 可直接交付 / B 小修后交付 / C 需较大调整
- 理由：<2~3 句>

## 二、问题总览
| 编号 | 维度 | 位置 | 问题 | 优先级 | 建议 |
| P-01 | 交互逻辑 | 新增工单页·提交按钮 | ... | P0 | ... |

优先级：P0 阻塞主流程或造成误解 / P1 影响效率或体验 / P2 优化项

## 三、页面完整性优化
## 四、布局排版优化
## 五、功能逻辑说明优化（含文案规范）
## 六、交互逻辑优化（含异常与空状态）
## 七、内容正确性检查
## 八、总结与实施建议
- 工时估算：P0 <x> 人日 / P1 <y> 人日 / P2 <z> 人日
- 分阶段：先修 P0 → 回归 → 再处理 P1/P2
```

规则：

- 每个问题必须带「位置」，让人能直接找到；
- 建议必须可执行（改哪句话、加哪个状态、调成多少 px），不写「优化一下交互」；
- 没有发现问题的维度也要写「未发现明显问题」，不要漏章节；
- 数量多时按优先级排序，P0 不超过 10 条，其余给清单不展开。

## 输出与自检

- 报告默认在对话里给；用户要文件时再落 Markdown/Word。
- 交付前自检：每个问题都有位置？优先级都有？建议都能落地？六个维度都覆盖？评估等级和理由是否一致？
- 只评审，**不要顺手改用户的原型文件**；用户要求修改时先确认范围再动手。
