# DOCX 需求文档结构规范（模板固化版）

本文件是 `assets/docspec.paxc.json` 的写作说明书。按本规范填充 docspec，`scripts/build_docx.js` 即可产出与模板一致的 DOCX。
章节骨架来自《【需求文档】安防综合管理平台V2.0-web端》，不得随意增删一级/二级章节。

## 0. 全局约定

- 字体：微软雅黑（正文与标题同字体）；正文 10.5pt（`size: 21`，半磅单位）。
- 页面：A4（11906×16838 twips），上下左右页边距 1134 twips（2cm）。
- 标题编号：一级 `1 产品概述`、二级 `1.1 项目背景`、三级 `功能描述`、四级 `首页看板`、五级 `设备告警`。
  编号只写在一级/二级标题文本里，三~五级标题不写编号。
- 表格：宽度 100%，全边框（A6A6A6，4），表头底纹 D9E2F3、加粗。
- 图片：居中，最大 585×900 px（等比缩放），图注在图片下方居中、9pt（`size: 18`）、灰色 595959。
- 图片路径相对 `--images`（原型目录下的 `images/`）。

## 2. 各章写作规范

### 1 产品概述

| 小节 | 写法 | 篇幅 |
| --- | --- | --- |
| 1.1 项目背景 | 2 段：行业/政策背景 + 本项目要解决什么问题、在哪个基座之上扩展 | 每段 80~150 字 |
| 1.2 业务场景 | 一句引导 + 5 条左右「场景名：能力说明」的要点 | 每条 30~60 字 |
| 1.3 产品定位 | 1 段：一句话定位 + 面向三类角色分别提供什么 | 100~150 字 |
| 1.4 阅读对象 | 要点列表：产品/研发/测试/干系人各自用途 | 4 条 |
| 1.5 项目干系人 | 两列表格「角色 / 职责」，5 行左右 | 职责 15~30 字 |
| 1.6 参考文档 | 两列表格「文档名称 / 说明」，列需求来源、原型、编写规范参考 | 3 行左右 |

### 2 系统说明

| 小节 | 形式 | 要求 |
| --- | --- | --- |
| 2.1 相关术语 | 表格「术语 / 说明」 | 只收本文档反复出现的专业词，6 行左右 |
| 2.2 系统清单 | 表格「系统 / 端 / 说明」 | 区分承载平台、本模块、范围外系统 |
| 2.3 系统拓扑图 | 图片 + 1 段说明 | 图片来自原型 `images/2_系统说明/u220.png` 一类拓扑图；图注「图 2-1 xxx」 |
| 2.4 系统架构图 | 引导句 + 分层要点 | 自下而上：感知层/接入层/平台层/业务层/展示层 |
| 2.5 系统角色定义 | 三列表格「角色 / 主要职责 / 权限范围」 | 角色粒度与 2.6 流程一致 |
| 2.6 系统业务流程 | 一句主线 + 4 步要点 | 统一为「发现 → 确认 → 处置 → 复盘」 |
| 2.7 全局功能结构图 | 三列表格「一级模块 / 二级功能 / 说明」 | 每个一级模块拆 2~3 行，覆盖全部页面 |
| 2.8 全局交互规范 | 引导句 + 6 条要点 | 提示、空态、搜索、弹窗、加载、刷新 |

### 3 功能需求

- 3.1 版本目标：1 段，说明本版本建成的能力与达成的闭环。
- 3.2 版本价值：4 条要点（补短板 / 提效率 / 规范流程 / 沉淀数据）。
- 3.3 需求列表：由 `reqTable` 内容块从 `xlsx.json` 自动生成。
  - `sheet`：工作表名（如「安防平台web端」）。
  - `filter`：`{ "column": 1, "values": ["心理管理","食堂管理"] }`，按列号过滤二级模块。
  - `columns`：`{ "module": 1, "point": 2, "desc": 4, "version": 5 }`，均为 0 基列号。
  - `versionDefault`：版本列为空时的默认值（如 `V1.0`）。
  - `headers` / `widths`：表头与列宽百分比，默认 `[6,12,14,58,10]`。
  - 表后补一句注释，说明哪些版本不在本次评审范围。

### 4 功能说明（核心章节）

每个模块严格四段结构：

1. `功能描述`（h3）：2 段，说明模块目标、覆盖页面。
2. `功能流程`（h3）：按 `（1）（2）…` 编号的步骤，5~6 步，覆盖主链路。
3. `规则限制`（h3）：4~5 条要点，写状态机、阈值、权限、边界。
4. `功能详明`（h3）：具体功能页面。

「功能详明」下的层级：

- 分组（可选）：加粗 12pt 蓝色（2E5496）段落 + 该组的功能描述/功能流程/规则限制。
- 功能页面：h4（`4.1.1` 级别不写编号），标题即页面名。
- 子功能：h5，缩进为 h4 的下级。

**每个功能页面的内容顺序（硬性）**：

```
h4/h5 页面标题
  → 原型截图（1~N 张，超长页自动分段，图注「图 <页面名>」/「图 <页面名>（2/3）」）
  → 需求说明表格（kvTable，两列：规则 | 说明）
  → 子功能 h5（递归同一顺序）
```

kvTable 行内容：

- 第一行固定 `功能描述` → 原型备注里的功能描述段落。
- 其后按原型备注的规则项逐行展开，如：`统计卡片`、`搜索`、`表格`、`交互说明`、`异常处理`。
- 左列 18% 宽（规则项名），右列 82% 宽（说明内容，可多段）。
- 备注缺失时用 `synth` 字段兜底写一段功能描述。

### 5 非功能需求

| 小节 | 条数 | 内容要点 |
| --- | --- | --- |
| 5.1 兼容适配需求 | 3 | 浏览器版本、分辨率、不支持的浏览器 |
| 5.2 性能需求 | 4 | 首屏/接口耗时、分页、AI 事件时延、刷新机制 |
| 5.3 安全保密 | 4 | 鉴权与权限、敏感数据、脱敏、传输存储加密 |
| 5.4 可拓展性 | 4 | 配置化扩展、场景横向扩展、事件类型扩展、与基座解耦 |

## 3. docspec 内容块语法

`chapters[].sections[].blocks[]` 支持以下类型：

```json
{ "type": "para",     "text": "一段正文" }
{ "type": "bullets",  "items": ["要点一", "要点二"] }
{ "type": "numbered", "items": ["步骤一", "步骤二"] }
{ "type": "table",    "headers": ["列1","列2"], "widths": [30,70], "rows": [["a","b"]] }
{ "type": "image",    "src": "2_系统说明/u220.png", "caption": "图 2-1 系统拓扑图" }
{ "type": "reqTable", "sheet": "安防平台web端", "filter": {...}, "columns": {...}, "headers": [...], "widths": [...] }
```

模块结构（`chapters[]` 中带 `modules` 的一章即第 4 章）：

```json
{
  "title": "4 功能说明",
  "intro": ["本章按模块分页说明……"],
  "modules": [
    {
      "title": "4.1 心理健康管理",
      "name": "心理健康管理",
      "desc": ["..."], "flow": ["..."], "rules": ["..."],
      "items": [
        { "title": "首页看板", "key": "a2-5-1_首页看板" },
        { "title": "测评管理", "key": "a2-5-4_测评管理",
          "sub": [{ "title": "测评结果", "key": "a2-5-4-1_____", "synth": "兜底描述" }] }
      ],
      "subs": [
        { "name": "分组名", "desc": ["..."], "flow": ["..."], "rules": ["..."], "items": ["..."] }
      ]
    }
  ]
}
```

- `items[].key` 必须等于原型 html 文件名去掉 `.html`（保留中文、括号、下划线），与 `notes.json` 的键一致。
- `synth` 仅在备注为空时使用，用于避免空白表格。
- `sub` 递归渲染为 h5，可再嵌套。

## 4. 备注（notes）→ 表格的解析规则

`capture.js` 抽取 Axure 右侧「需求说明/页面备注」面板的 `innerText`。`build_docx.js` 的 `parseNotes` 规则：

1. 按空行分块、块内按行拆分，去掉空行与 `功能`/`说明`/`变更记录` 等面板装饰词。
2. 从 `功能描述` 之后开始收集正文，直到遇到第一个规则项 → 即 `desc`。
3. 规则项的判定：下一行以 `交互逻辑` / `交互规则` 开头，或本行是 `交互说明` / `异常处理` / `异常情况` / `交互逻辑说明`。
4. 规则项行 + 其后的内容行组成 kvTable 的一行。

因此原型备注建议按「功能描述 / 交互说明 / 异常处理 / 业务规则」四类写，每类单独一段。
